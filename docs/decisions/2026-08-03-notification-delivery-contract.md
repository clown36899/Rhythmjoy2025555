# 알림 전달·읽음 상태 계약

- 날짜: 2026-08-03
- 상태: 채택, 배포 전

## 배경

기존 구현은 인앱 알림함, Web Push 구독, 사용자 알림 선택, 운영체제 알림 제거를 하나의 흐름처럼 다뤘다. 그 결과 큐 소비자가 멈추면 종도 비었고, 기기 구독 행마다 설정이 달라질 수 있었으며 사용자별 읽음 상태가 없는 자유게시판 배지가 계속 남았다.

## 결정

1. 우측 상단 종은 로그인 사용자별 인앱 미확인 피드다. 푸시 신청 여부와 무관하게 이전 방문 이후 새로 등록되고 아직 끝나지 않은 이벤트 및 사용자 대상 알림을 보여준다. 큐 처리가 늦어져도 등록 뒤 이미 방문한 사용자에게 과거 항목을 뒤늦게 넣지 않는다.
2. 알림 설정은 단말 Web Push 전달 여부와 대상 선택만 제어한다. 설정은 사용자 단위, PushSubscription은 기기·브라우저 단위로 저장하고 한 사용자 설정을 모든 활성 기기에 적용한다.
3. 인앱 알림함의 서버 읽음 상태를 기준 데이터로 사용한다. 종을 열면 표시된 미확인 항목을 그 사용자에게만 읽음 처리하고 다음 열기부터 제외한다. 운영체제 알림 탭은 해당 출처 한 건만 읽음 처리한다.
4. 새 이벤트 알림은 결정적 출처 ID로 중복 저장을 막는다. 종료된 이벤트는 읽지 않았더라도 종과 배지에서 제외한다. 오래된 대기 항목은 단말 Push를 만료시키되 사용자의 이전 방문 뒤 등록된 아직 유효한 이벤트는 인앱 피드에 보존한다.
5. Web Push는 최선 노력 전달 수단이다. TTL, Topic, 영구 실패 구독 정리, 성공 기기 기록, 제한된 지수 백오프를 적용한다. 인앱 저장 성공은 Push 실패와 독립적이다.
6. 자유게시판 새 글 표시는 `user_id + post_id` 읽음 상태를 사용한다. 본인 글과 비공개 글은 새 글 수에서 제외하고, 목록 클릭과 직접 링크 진입 모두 읽음으로 기록한다. 비로그인 사용자는 해당 브라우저의 로컬 읽음 기록만 사용한다.
7. 최초 배포 이전의 대기열은 발송하지 않고 기준선 처리한다. 이후에도 한 번에 4건 이상이 밀리면 개별 단말 Push를 억제하고 인앱 피드만 유지한다. 배포 중에는 cron을 먼저 중지하고 데이터·서버 준비가 모두 끝난 뒤 마지막에 다시 활성화한다.
8. 최초 전환에서는 관리자 포함 기존 단말 구독을 서버에서 모두 제거하고 모든 기존 구독자의 마스터·오늘 일정·새 이벤트 설정을 끈다. 사용자가 알림 설정을 다시 저장한 시점부터 새 단말 구독을 활성화한다. 이후 배포는 재설정한 정규 사용자 설정을 덮어쓰지 않는다.
9. 최초 전환 시 사용자별 미읽음 상태변경 공지를 고정 출처 ID로 한 건 생성한다. 기존 큐와 브라우저 로컬 알림은 공지 숫자에 섞지 않으며, 공지 수가 종 숫자에 동적으로 반영되고 사용자가 종을 열면 해당 사용자에게만 읽음 처리된다.

## 근거 표준

- W3C Push API와 RFC 8030의 구독·전달 모델에 따라 구독을 기기별 전달 주소로 취급한다.
- RFC 8030의 TTL 및 Topic 의미를 적용해 오래된 메시지와 중복 전달을 제한한다.
- RFC 8292의 VAPID 인증을 유지하며 404·410 및 VAPID 불일치 구독은 영구 실패로 정리한다.
- Notifications API의 사용자 동작 중심 권한·표시 원칙에 따라 앱 포커스나 일반 이동을 읽음으로 간주하지 않는다.

## 결과

큐나 단말 Push가 일시적으로 실패해도 종의 사용자별 피드는 유지된다. 여러 기기에서 같은 계정으로 읽은 상태가 서버에서 일치하며, Push 설정을 하지 않은 사용자도 새 이벤트를 종에서 확인할 수 있다.
