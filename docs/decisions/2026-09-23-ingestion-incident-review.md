# 수집 장애의 성공 원장 대조와 당일 재시도 보고

- 날짜: 2026-09-23
- 상태: 진단 절차 및 기존 결과/알림 개선. 검증·운영 적용 결과는 ISSUE_LOG 참조.

## 확인한 오류와 근거

이번 조사에서 에이전트가 성공 원장을 먼저 대조하지 않아 판단을 여러 번 수정했다. 최근 로그인 오류를 전체 원인으로 설명했고, 보조 홈페이지의 Notion 이동을 실제 수집 링크와 혼동했다. 실제로 오늘 후보는 9/21부터 존재했으며 먼저 실패한 단계는 잘린 날짜별 본문과 DJ 추출이었다. 일반 브라우저와 수집 브라우저의 세션 차이는 있었지만, 새 Mini PC 프로필은 로그인 없이 현재 공개 원문을 읽었다. 쿠키 부재만으로 로그인 작업이 필수라고 안내한 것도 근거가 부족했다.

이전 빈도 축소 역시 완료 항목까지 재처리하는 원인을 고치지 못했다. 항목·회차 선정 대신 예약 횟수를 조정한 접근을 철회했다. 복구 시 요청 ID/상태와 API의 실제 ID/상태도 달랐다. 내용 식별 보호로 새 ID가 반환됐고 기존 잘못된 후보는 서버 판정에 따라 duplicate가 됐다. 요청 의도를 실행 결과로 보고하면 안 된다.

## 당일 재시도가 멈춘 것처럼 보인 경로

증상 → 판정 → 부작용 → 원장/외부 결과:

- 소셜클럽 오류가 남음 → 문서 오류를 출처 단위 `remainingSources`에 기록 → 알림에 신규 후보 0건·미완료 출처 1개만 표시 → 같은 실행의 오늘 공개 등록 성공과 다른 게시글 오류를 구분하기 어려움.
- 다음 실행은 공개 일정의 오늘 미확정 정규 회차만 선정 → 이미 등록됐으므로 0곳 → 브라우저를 열지 않음. 이는 실패 회차 누락이 아니라 성공 회차 재처리 중단이었다.
- 동일 문제 알림은 24시간 억제 → 반복 알림 없음. 이 정책은 예약 실행과 독립이며 재시도 중단의 증거가 아니다.

실제 근거:

- Mac의 9/23 08:00, 09:34, 10:38, 11:44, 12:30, 14:30, 15:30 실행에서 `sosyalclub_swing`을 재시도했다. 앞선 실행들은 브라우저 종료 또는 로그인 차단으로 실패했다.
- Mini PC `20260923_160943_2761882`: 월간 게시글 `Dc3osQDkzci`에서 추출 검토 오류가 났지만 오늘 게시글 `Ddiej0hkxPG`는 등록됐다. 공개 이벤트 `640a956a-5a0d-43fb-a771-4913ff7799a6`, 날짜 9/23, DJ 쓴귤을 확인했다.
- 자연 예약 `20260923_163000_2765591`: 당일 대상 0, 브라우저 미실행. 운영 공개 API를 다시 읽어 오늘 소셜클럽 1건과 수집 대상 정규 미확정 0곳을 확인했다. 이 결과가 모든 클럽의 미발견 공지까지 없다는 뜻은 아니다.

## 기존 구현 및 변경 경계

**일부 있음.** 재시도 선정은 `findUnresolvedTodaySocialSources`와 native `main`, 항목 완료는 기존 진행 파일, 등록 완결성은 `pipeline.reconciliation`, 알림 억제는 `telegram-notification-policy.mjs`가 이미 소유한다. 빈틈은 실제 선정 결과가 결과/알림으로 전달되지 않는 부분이다. 재시도 선정을 다시 구현하거나 잔여 출처 전체를 합치지 않는다.

관련 목적을 확인한 이력은 fe2b77c6(실패 체크포인트 보호), dcd369e0(중단 재개), e38beda0(단계별 진단), 8524db2b(후보 저장과 공개 등록 구분) 및 9/23 당일 재시도 결정이다. 스킬의 전역 프로세스 종료 지침은 a4dc7345에서 유래해 bccf370fa 개편 때 남았지만, 현재 공유 호스트의 기존 자식 프로세스 정리와 충돌하므로 제거한다. 실제 다른 서비스를 종료했다는 증거는 없다.

- 기존 `pipeline.reconciliation`에 `sameDayRetry` 관측값을 추가한다. 행사 날짜, 선정 출처, 남은 출처, 원장 확인 여부만 담으며 DB·진행 파일·큐·상태값을 새로 만들지 않는다. 기존 문서 완결성 수치는 오늘 회차를 발견하지 못한 실행이나 대상 없는 실행을 표현하지 못하므로 별도 관측값이 필요하다.
- 기존 문제 알림에 공개 등록/갱신 수와 당일 재시도/중단/판정 보류를 연결한다. 다른 게시글 오류는 숨기지 않는다. 정상 실행 안내 제외 및 같은 문제 24시간 억제는 유지한다.
- AGENTS와 기존 수집 스킬에 성공 원장 우선 대조를 연결한다. 링크·로그인·일정·저장·등록 단계를 구분하고 실제 응답과 공개 결과로 완료를 보고한다. Mini PC 운영 문서도 실제 수집 프로필 검증을 로그인 요청보다 앞에 둔다.

새 수집기·원장·예약·등록 경로가 없어 책임 중복과 데이터 마이그레이션은 없다. 결과 필드가 없는 예전 로그와 알림은 그대로 읽는다. 롤백은 이전 runtime의 두 모듈로 복원하며 진행 상태·등록 결과를 되돌리지 않는다.

## 불변조건 및 검증 범위

- 당일 실패는 다음 기존 예약에서 재시도하며 전날·지난 회차는 반복하지 않는다. 성공·휴무·관리자 삭제와 KST 날짜 경계를 유지한다.
- 실제 메인 루프에서 API 422/503 → 다음 실행 성공 → 공개 일정 반영 → 이후 브라우저/저장 호출 0을 검사한다. API가 반환한 후보 ID를 등록 요청이 사용하는지도 함께 확인한다.
- 기존 부분 성공 보존·다중 회차·원장 조회 실패·레거시 진행 파일·날짜 경계·등록 충돌·잠금 검사를 재사용한다. 알림 검사는 다른 문서 실패와 오늘 성공의 공존, 오늘 미완료, 원장 확인 불가 및 24시간 억제를 검증한다.
- 선택 함수를 바꾸지 않았으므로 운영 데이터를 지우거나 실패를 인위적으로 만들어 테스트하지 않는다. 전체 사이트 빌드·웹 배포·신규 전체 수집·기기 재부팅도 제외한다. 실제 runtime 적용은 유휴 상태의 두 모듈만 교체하고 다음 실행 명령과 공개 원장을 읽어 확인한다.
