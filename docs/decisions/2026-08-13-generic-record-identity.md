# 범용 레코드 식별자 정책

- 날짜: 2026-08-13
- 상태: 채택, 운영 반영·복원 완료

## 배경

Cafe24 호환 데이터 계층은 여러 논리 테이블을 `generic_records(table_name, record_id, data_json)`에 저장한다. 기존 ID 계산은 명시적 ID가 없는 행의 `user_id`를 모든 테이블에서 레코드 ID로 사용했다. `user_id`가 소유권일 뿐인 자유게시판 글처럼 사용자당 여러 행을 허용하는 테이블에서는 같은 사용자의 다음 insert가 기존 행을 덮어썼다.

## 결정

범용 레코드 ID는 다음 우선순위로 결정한다.

1. 기기 구독과 선언된 상호작용 복합 키처럼 테이블별 결정적 식별 규칙을 먼저 적용한다.
2. 기존 행에 명시적 `id`가 있으면 그 ID를 보존한다.
3. upsert가 conflict 키를 지정하면 일부가 아닌 모든 키 값을 결합한다.
4. `code`, `key`, `token`, `endpoint`처럼 명시된 자연 키를 사용한다.
5. `user_id` 단독 키는 사용자당 한 행인 `board_admins`, `board_users`, `user_home_menu_settings`에만 사용한다.
6. 위 규칙이 없는 신규 행에는 매번 새 UUID를 발급한다.
7. 계산된 ID는 저장 키뿐 아니라 응답과 후속 수정·삭제에 쓰이는 JSON `id`에도 기록한다.

범용 레코드의 ID는 불투명 식별자로 취급한다. 과거 고정 데이터에는 숫자 ID가 남을 수 있지만 새 레코드는 UUID가 될 수 있으므로, UI와 API 소비자는 `number | string`을 허용하고 `Number()`·`parseInt()`로 강제 변환하지 않는다. `<select>` 같은 문자열 입력에서 숫자형 레거시 ID만 안전하게 숫자로 복원하고 그 밖의 값은 원문 문자열로 보존한다.

## 복원 원칙

덮어쓴 운영 데이터는 전체 백업을 되감지 않는다. 현재 행을 새 ID로 먼저 복제해 보존하고, 백업에서 확인된 서로 다른 과거 버전을 각각 독립 레코드로 추가한다. 복원 전 제목·작성자·생성일과 관련 댓글·상호작용 범위를 확인하며 모든 변경은 한 트랜잭션에서 수행한다.

## 결과

같은 사용자가 여러 글·댓글·소유 콘텐츠를 생성해도 서로 다른 레코드로 유지된다. 사용자 단위 설정과 복합 상호작용의 결정적 중복 방지는 그대로 유지되고, 기존 explicit ID를 가진 upsert가 다른 물리 키로 복제되는 문제도 방지한다.

운영에서는 현재 글을 새 UUID로 이동하고 마지막 두 정상 백업의 과거 글을 각각 독립 ID로 복원했다. 공개 API 기준 전체 게시물은 14건에서 16건, 자유게시판은 12건에서 14건으로 회복했으며 기존 제주 글 링크와 읽음 2건도 보존했다.
