# 관리자 소셜 삭제 우선순위

- 날짜: 2026-09-13
- 상태: 배포 완료 (542e6e7d, 공개 버전 1789289048441)

관리자가 일정에서 삭제한 소셜 회차는 반복 규칙, 공식 휴무 표시, 재수집된 DJ 정보로 자동 복원하지 않는다. 미수집 일정 보존은 관리자의 명시적 삭제를 무효화하지 않는다. 경성홀 RSF 대관 사례가 계기지만 장소나 특정 날짜 전용 예외는 만들지 않는다.

기존 scraped_events의 excluded 상태와 structured_data._exclusion을 삭제 원장으로 재사용한다. 삭제 ID 및 날짜·장소 소셜 회차를 기록하며, 관리자 삭제 3경로(직접 이벤트 API·generic API·화면의 /api/delete-event)가 같은 트랜잭션 저장기를 호출한다. 공통 이벤트 저장기 두 곳과 정규 조정·수집 후보·등록 경로가 같은 식별 함수를 사용한다. 진행 중 저장과 삭제의 경쟁은 MySQL 연결 잠금 하나로 직렬화한다. 외부 API의 기존 트랜잭션은 커밋/롤백까지 잠금을 유지한다. 새 테이블·큐·상태값은 없으며 스키마 마이그레이션이 필요 없다.

기존 제외 상태만으로는 정규 생성기가 관리자 삭제를 알 수 없었고, 원장 조회만 추가하면 조회 후 삭제와 저장이 엇갈릴 수 있어 공통 삭제/잠금 모듈이 필요했다. 일반 조정 교체·정리와 비관리자 삭제는 이 원장을 작성하지 않는다. 행사·강습·졸공·다른 날짜/장소를 소셜 삭제에 포함하지 않는다. 삭제된 정확한 ID는 분류 변경으로 복원할 수 없다.

복원은 관리자의 명시적 제외 기록 해제 후 진행한다. 기존에 삭제된 행은 근거 없이 추정 복원/제외하지 않는다. 배포를 롤백하면 이전 생성기는 이 삭제 기록을 읽지 않으므로 재생성 방지를 유지하려면 조정 작업을 중지하거나 함께 보완해야 한다. 원장은 자동 삭제하지 않는다.

향후 UI 대안은 이번 회차 완전 삭제와 휴무 사유 표시를 구분하는 것이다. RSF처럼 별도 행사가 존재한다는 사실만으로 정규 소셜을 자동 취소하지 않으며 관리자 확인 또는 명시적 휴무 근거가 필요하다.
